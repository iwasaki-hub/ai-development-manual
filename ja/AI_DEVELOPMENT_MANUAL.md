# AI開発マニュアル（共通版）

- バージョン：1.0
- 対象：Webアプリ、モバイルアプリ、API、業務ツール、学習用プロジェクトなど
- 目的：AIとのやり取りを整理し、開発の品質・再現性・継続性を高める

---

## 1. 基本方針

### 1.1 AIとの協業ルール

AIは、単にコードを出力するだけでなく、設計・実装・検証・説明を支援する開発パートナーとして利用します。

- **小さな単位で進める：** 一度に多くの変更を行わず、確認しやすい作業単位に分けます。
- **現状を確認してから変更する：** 既存コードや設定を見ずに、ファイル名・構成・実装を決めつけません。
- **根拠を明確にする：** 不明点は不明と伝え、事実・推測・提案を区別します。
- **動作確認を重視する：** コードを書いたことと、正常に動いたことを同一視しません。
- **既存仕様を尊重する：** 明示的な依頼がない限り、関係のない機能やデザインを変更しません。
- **ユーザーの理解を助ける：** 変更理由、操作手順、確認方法を分かりやすく説明します。
- **セキュリティを守る：** APIキー、パスワード、アクセストークンなどの秘密情報をソース管理に含めません。
- **決定事項を記録する：** 長期的に重要な仕様や命名規則は、プロジェクト文書に残します。

### 1.2 AIに最初に渡す共通指示

新しい開発チャットの冒頭で、必要に応じて次の指示を使います。

> あなたは、私のソフトウェア開発を支援する開発パートナーです。  
> まずプロジェクトの目的、現在の構成、既存コード、制約を確認してください。情報が不足している場合は、作業に必要な質問をしてください。  
> 一度に大量の変更をせず、検証可能な小さなステップに分けて進めてください。  
> 既存の動作やデザインを、依頼なく変更しないでください。  
> コードを提案するときは、対象ファイル、変更箇所、変更理由、実行・確認方法を示してください。既存ファイルを修正する場合、部分修正かファイル全体の置き換えかを明確にしてください。  
> 実際に実行していないテストやデプロイを、完了したと表現しないでください。問題があれば原因の候補と確認手順を示してください。  
> 私が初心者でも追えるよう、専門用語やコマンドを必要に応じて説明してください。  
> 作業の最後に、完了内容、変更ファイル、確認結果、未解決事項、次のステップ、GitHub Desktopでコミットする適切なタイミングをまとめてください。

## 5. Git・GitHub Desktop運用ルール

### 5.1 基本ルール

- 意味のある小さな作業単位でコミットします。
- 変更内容を確認してからコミットします。
- ひとつのコミットに、無関係な機能や修正を混在させません。
- コミット前に、動作確認と差分確認を行います。
- 重要な機能が完成し、動作確認できたタイミングをコミット候補とします。
- プッシュ前に、秘密情報や不要ファイルが含まれていないか確認します。
- 大きな変更の前に、現在の変更をコミットするか、作業状態を安全に保存します。

### 5.2 GitHub Desktopの基本手順

1. 左側の「Changes」で変更ファイルを確認します。
2. 各ファイルの差分を確認し、意図しない変更がないか見ます。
3. 「Summary」に変更内容を短く入力します。
4. 「Commit to ...」を押してコミットします。
5. GitHubに反映する場合は「Push origin」を押します。
6. GitHub上のリポジトリで変更が反映されていることを確認します。

### 5.3 コミットメッセージ例

- `Initialize project structure`
- `Add memo creation feature`
- `Fix memo deletion bug`
- `Improve mobile layout`
- `Add input validation`
- `Update project documentation`

コミットメッセージは、何を変更したかが分かる具体的な内容にします。

### 5.4 秘密情報の管理

- `.env` などの秘密情報を含むファイルをGitに追加しません。
- `.gitignore` の設定だけに頼らず、コミット対象も確認します。
- 誤って秘密情報を公開した場合、ファイルを削除するだけでは不十分なことがあります。該当するキーやパスワードを無効化・再発行してください。

## 6. 実装・確認チェックリスト

### 作業を始める前
- [ ] 目的と完成条件が明確
- [ ] 関係する既存コード・設定を確認
- [ ] 変更してはいけない範囲を確認
- [ ] 不明点やリスクを整理

### 実装中
- [ ] 小さな変更単位で進行
- [ ] 既存の命名規則・構造を尊重
- [ ] 入力値やエラーケースを考慮
- [ ] 認証・認可・秘密情報を適切に扱う
- [ ] 不要な依存関係や大規模変更を避ける

### 実装後
- [ ] 開発サーバーやビルドを確認
- [ ] 変更した機能を確認
- [ ] 関連する既存機能への影響を確認
- [ ] PCとスマートフォンの表示を必要に応じて確認
- [ ] エラー・境界値を必要に応じて確認
- [ ] 実施していない確認を明確にした
- [ ] Git差分と秘密情報の混入を確認
- [ ] 必要なドキュメントを更新
- [ ] コミット・プッシュのタイミングを判断
- [ ] 次のステップと未解決事項を記録

## 7. AIに回答してもらう際の希望形式

作業の種類に合わせて、AIには次の情報を簡潔に示してもらいます。

1. **今回の目標**
2. **現在分かっていること／不足している情報**
3. **変更方針**
4. **対象ファイル**
5. **具体的な手順またはコード**
6. **実行・確認方法**
7. **期待される結果**
8. **問題が起きた場合の切り分け方法**
9. **GitHub Desktopでコミットするタイミング**
10. **次に行うこと**

簡単な質問では、必要な項目だけに絞ります。回答を長くすること自体を目的にしません。

## 8. マニュアルの改善

- 実際の開発で使いにくかったルールやテンプレートは、具体例をもとに改善します。
- 特定のプロジェクトだけで必要なルールは、共通マニュアルではなく各プロジェクトの文書に記録します。
- ルール同士が矛盾する場合は、セキュリティとユーザーが明示した要件を優先し、矛盾を解消します。
- マニュアルを変更したら、READMEとバージョン履歴も必要に応じて更新します。
