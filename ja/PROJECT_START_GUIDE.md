# プロジェクト開始手順書

## 1. 目的

この手順書は、AIと協力して新規または既存のソフトウェアプロジェクトに取り組み始める際の標準的な進め方を定めるものです。

プロジェクトごとに開発の進め方が大きく変わらないようにし、計画、実装、テスト、Gitによる変更管理を一貫した手順で進めます。

共通の開発ルールについては、`AI_DEVELOPMENT_MANUAL.md` を参照してください。

## 2. 使用するファイル

新規・既存どちらのプロジェクトでも、使用する言語に応じて次のマニュアルと開始プロンプトを使用します。

- `ja/AI_DEVELOPMENT_MANUAL.md`：AIと協力して開発する際の共通ルール
- `templates/PROJECT_START_PROMPT.md`：日本語の開始プロンプト

英語で開発を進める場合は、次のファイルを使用します。

- `en/AI_DEVELOPMENT_MANUAL.md`：英語の共通ルール
- `templates/PROJECT_START_PROMPT.en.md`：英語の開始プロンプト

開始プロンプトの情報欄は、分かる範囲で記入してください。未確定の項目をすべて埋める必要はなく、重要な点はAIと相談できます。実際のパスワード、トークン、秘密鍵などは記入しないでください。

## 3. 開発開始前の準備

開始前に、分かる範囲で次の項目を整理します。プロンプトには目的、想定利用者、対象プラットフォーム、機能の範囲、受け入れ条件、技術・運用上の制約、データとプライバシー上の制約を記入できます。

- プロジェクト名
- 作成したいものとその目的
- 想定する利用者
- 必要な機能
- 使用したい技術や開発環境
- デザインや操作性の希望
- 制約や注意事項
- 現在の進捗
- 今回取り組みたい作業

まだ決まっていない項目は無理に埋めず、作業に必要な重要事項をAIと相談します。

## 4. AIへの指示

1. 使用言語に対応したマニュアルと開始プロンプトをAIに渡します。
2. 分かる範囲でプロジェクト情報を記入します。新規か既存かを示し、既存ならリポジトリや作業フォルダを指定します。
3. 既存プロジェクトでは、AIに `AGENTS.md` などの指示、README、関連コード・設定、ブランチとGit状態を確認させます。既存の未コミット変更や未追跡ファイルは保持します。
4. 新規プロジェクトでは、既存コードの有無を確認し、目的、必要な機能、対象外、制約、受け入れ条件を整理します。
5. AIに確認できた現状と必要な作業を整理させ、計画を提示させます。
6. 重要な設計判断や複数の妥当な選択肢がある場合は、影響を確認して合意してから進めます。具体的な作業が明示され、重大な不明点や新たなリスクがなければ、不必要な再承認を求めず依頼範囲内で進めます。

依頼範囲を超える判断、重大な不明点、または新たな重大リスクがある場合は、実行前に確認します。

## 5. 実装の進め方

開発は、確認しやすい小さな工程に分けて進めます。

各工程では、原則として次の順序を守ります。

1. 今回の目的と完了条件を確認する。
2. 変更対象のファイルと変更理由を確認する。
3. 実装する。
4. 実行やテストによって動作を確認する。
5. 結果と残っている課題を整理する。
6. 次の工程に進む前に内容を確認する。

一度に多くの変更を加えることは避け、問題が発生した際に原因を特定しやすい状態を保ちます。

既存の機能やデザインに影響する場合は、変更前にその影響を確認します。

## 6. テストと確認

変更した内容に応じて、適切な方法で動作を確認します。

- 実装した機能が期待どおりに動作するか
- 既存の機能に問題が発生していないか
- エラーや警告が発生していないか
- 必要な画面や操作が正しく動作するか

実行していないテストを、実施済みとして報告してはいけません。

確認できた事実、未確認の事項、推測を区別して報告します。

## 7. Gitによる変更管理

利用者が選んだGitクライアントと、プロジェクトの既存ワークフローに従って変更を管理します。

1. 作業開始前に、現在のブランチと同期状態を確認します。
2. 変更したファイルと差分を確認します。
3. 意味のある作業単位でコミットします。
4. コミットメッセージには変更内容を簡潔に記載します。
5. Pushは利用者の依頼・許可がある場合に行い、動作確認後に適切なタイミングを選びます。
6. Push後、GitHub上に変更が反映されていることを確認します。

コミットやPushの前には、不要な変更や機密情報が含まれていないか確認します。

APIキー、パスワード、アクセストークンなどの秘密情報をリポジトリに登録してはいけません。

削除や上書きなど、元に戻すことが難しい操作を行う場合は、実行前に影響を確認します。

## 8. 作業完了時の報告

各工程が完了したら、次の内容を整理します。

- 完了した作業
- 変更したファイル
- 実施したテストとその結果
- 未解決の問題や注意点
- 次に推奨する作業
- コミット・Pushを行うべきタイミング

重要な判断や依頼範囲外の操作など、ユーザー確認が必要な場合は、結果と影響を説明し、確認を得てから進みます。明示された依頼の範囲内で確認済みの手順を進める際は、不要な確認を繰り返しません。

## 9. プロジェクトの継続

次の作業を始める際は、前回の進捗、変更内容、残っている課題を確認します。

必要に応じて、関連ファイルやGitHub上の最新の変更を確認し、現状と異なる前提で作業しないようにします。

作業の継続に必要な情報が不足している場合は、推測で補わず、確認してから進めます。

## 10. 基本方針

- 小さな工程に分けて進める。
- 実装前に目的と変更内容を確認する。
- 既存の機能や設計を尊重する。
- テスト結果を事実に基づいて報告する。
- GitHubで変更履歴を管理する。
- 不明点を放置せず、必要に応じて質問する。
- 各工程の完了を確認してから次に進む。
